cc-lb 한눈에

Claude Code · OpenCode · pi · Senpi 같은 코딩 에이전트의 ANTHROPIC_BASE_URL만 cc-lb로 돌려주면, 그 안에서 인증 브로커링 · 사용량 쿼터 · 감사 로그 · 메트릭을 강제할 수 있는 Rust 정적 musl 바이너리입니다. 클라이언트 코드는 단 한 줄도 안 바꿔도 됩니다.

2분 컷 Quick Start 내 상황에 맞는 길 찾기 Config 빌더 열기

이 가이드는 레퍼런스가 아니라 use case 모음입니다. "지금 내 상황이면 어떤 옵션을 켜야 하나" 한 가지만 골라서 따라하면 됩니다. 전체 옵션 레퍼런스가 필요하면 치트시트와 examples/cc-lb.toml을 참고하세요.

Quick Start · 2분 컷

실제 Anthropic API 키 하나만 있으면 됩니다. 검증된 흐름

  1. 빌드

    repo 루트에서:

    bash
    cargo build --workspace
# 결과: target/debug/cc-lb

    2분 이상 걸리면 정상입니다 (Wasmtime/Cranelift 의존성 포함). 한 번 빌드해두면 캐시됩니다.

  2. 최소 config 파일 만들기

    아무 곳이나 quickstart.toml 생성:

    toml
    [listener]
proxy_addr   = "127.0.0.1:8080"
admin_addr   = "127.0.0.1:9090"
metrics_addr = "127.0.0.1:9091"

[body]
messages_cap_bytes = 33554432
files_cap_bytes    = 104857600

[timeouts]
upstream_total_secs     = 600
drain_secs              = 60

[runtime]
data_dir = "./data"


[storage]
kind = "sqlite"
path = "./data/cc-lb.sqlite"

[aead]
key_env = "CC_LB_MASTER_KEY"

[observability]
tracing_level         = "info"
log_redaction         = true
user_prompt_redaction = false

[[admin.auth.providers]]
kind = "static_token"
id = "quickstart"
token_env = "CC_LB_ADMIN_TOKEN"

[circuit_breaker]
failures_to_open     = 5
window_secs          = 10
half_open_after_secs = 30

[bulkhead]
max_conns_per_upstream  = 50
semaphore_per_upstream  = 100
    팁 인터랙티브 Config 빌더에서 옵션 골라 자동 생성할 수도 있습니다.

  3. 환경변수 (마스터키 + admin provider 토큰 + upstream credential)

    [aead]의 key_env와 [[admin.auth.providers]]의 token_env가 가리키는 secret을 설정합니다. Quick start는 ./data/cc-lb.sqlite를 사용하고, upstream/principal/API key는 서버가 뜬 뒤 admin v1 API로 생성합니다.

    bash
    export CC_LB_MASTER_KEY=$(openssl rand -hex 32)   # 64자 hex 필수
export CC_LB_ADMIN_TOKEN=$(openssl rand -hex 24)
export ANTHROPIC_UPSTREAM_API_KEY=sk-ant-api03-...

  4. 띄우기 전에 한 번 검증

    bash
    ./target/debug/cc-lb config validate --config quickstart.toml
# "validation: ok" → exit 0

    네트워크 호출 없이 TOML 파싱, 마스터키 형식, plugin dry-load, TLS 파일 존재만 확인합니다.

  5. 서버 실행

    bash
    ./target/debug/cc-lb serve --config quickstart.toml

    3개 리스너가 동시에 뜹니다: :8080 프록시, :9090 관리 API + UI, :9091 Prometheus.

  6. Admin v1 API로 upstream/principal/managed key 생성

    DB upstream이 provider kind와 credential 위치를 소유하고, DB principal이 client identity를 소유합니다.

    bash
    # upstream creation: POST /admin/v1/upstreams
curl -s -X POST http://127.0.0.1:9090/admin/v1/upstreams \
  -H "Authorization: Bearer $CC_LB_ADMIN_TOKEN" \
  -H "content-type: application/json" \
  -d '{"name":"anthropic","kind":"anthropic_api_key","base_url":"https://api.anthropic.com","api_key_env":"ANTHROPIC_UPSTREAM_API_KEY"}'

# principal creation: POST /admin/v1/principals
principal_id=$(curl -s -X POST http://127.0.0.1:9090/admin/v1/principals \
  -H "Authorization: Bearer $CC_LB_ADMIN_TOKEN" \
  -H "content-type: application/json" \
  -d '{"name":"api-key","kind":"machine","allowed_models":["*"]}' | jq -r .id)

# managed API key issuance: POST /admin/v1/principals/{principal_id}/keys
CC_LB_PROXY_KEY=$(curl -s -X POST "http://127.0.0.1:9090/admin/v1/principals/$principal_id/keys" \
  -H "Authorization: Bearer $CC_LB_ADMIN_TOKEN" \
  -H "content-type: application/json" \
  -d '{"label":"quickstart"}' | jq -r .plaintext_key)

    api_key_env는 생성/수정 시점에만 읽는 환경변수 이름입니다 — 값은 즉시 암호화되어 저장되고 변수명 자체는 저장·반환되지 않으므로 secret을 나중에 복원할 방법은 없습니다. 키 label은 생략하거나 빈 문자열로 둘 수 있고, 유효하지 않은 비어있지 않은 label(NUL 바이트, system. 접두사)은 400 invalid_input을 반환합니다. label 없는 키는 v1 목록에서 null로 표시됩니다.

  7. 발급한 managed API key로 호출 (가장 중요한 단계)

    앞 단계에서 한 번만 표시된 CC_LB_PROXY_KEY를 x-api-key로 보냅니다. cc-lb는 이 키의 DB principal을 인증하고, DB에서 선택한 upstream의 credential로 요청을 전달합니다.

    bash
    # 헬스 체크 먼저
curl -s http://127.0.0.1:8080/healthz
# 응답: ok

# 실제 호출 (non-streaming)
curl -s -X POST http://127.0.0.1:8080/v1/messages \
  -H "x-api-key: $CC_LB_PROXY_KEY" \
  -H "anthropic-version: 2023-06-01" \
  -H "content-type: application/json" \
  -d '{
    "model": "claude-sonnet-4-5-20250929",
    "max_tokens": 32,
    "messages": [{"role": "user", "content": "ping"}]
  }'

# 실제 호출 (SSE 스트리밍)
curl -N -X POST http://127.0.0.1:8080/v1/messages \
  -H "x-api-key: $CC_LB_PROXY_KEY" \
  -H "anthropic-version: 2023-06-01" \
  -H "content-type: application/json" \
  -d '{
    "model": "claude-sonnet-4-5-20250929",
    "max_tokens": 64,
    "stream": true,
    "messages": [{"role": "user", "content": "stream please"}]
  }'

  8. 트래픽이 실제로 도는지 확인 (이게 "로드 밸런싱 검증")

    위 호출 직후:

    bash
    # Prometheus 카운터로 본 트래픽
curl -s http://127.0.0.1:9091/metrics | grep -E '^cc_lb_requests_total'
# upstream="anthropic", status="200" 등이 값 1 이상으로 늘어야 함

# Admin UI에서 시각적 확인 (브라우저)
xdg-open http://127.0.0.1:9090/ 2>/dev/null

# Admin REST (감사 로그)
curl -s -H "Authorization: Bearer $CC_LB_ADMIN_TOKEN" \
  http://127.0.0.1:9090/admin/v1/audit | head -c 400
    잘 됐나? cc_lb_requests_total이 늘었고 응답 본문이 정상 Anthropic JSON이면 프록시 path가 끝까지 통과한 것입니다. 이 상태에서 클라이언트(Claude Code, OpenCode 등)의 ANTHROPIC_BASE_URL을 http://127.0.0.1:8080로 바꾸면 됩니다.

  9. 클라이언트 붙이기

    bash
    # 예: Claude Code
ANTHROPIC_BASE_URL=http://127.0.0.1:8080 \
  ANTHROPIC_API_KEY=$CC_LB_PROXY_KEY \
  claude

# 예: OpenCode
ANTHROPIC_BASE_URL=http://127.0.0.1:8080 \
  ANTHROPIC_API_KEY=$CC_LB_PROXY_KEY \
  opencode

# 예: pi
ANTHROPIC_BASE_URL=http://127.0.0.1:8080 \
  ANTHROPIC_API_KEY=$CC_LB_PROXY_KEY \
  pi

# 예: Senpi (요청 종류 분류, 세션 헤더 없음)
ANTHROPIC_BASE_URL=http://127.0.0.1:8080 \
  ANTHROPIC_API_KEY=$CC_LB_PROXY_KEY \
  senpi --provider anthropic --model claude-sonnet-4-5
    Senpi 세션 ID 기본 Anthropic provider는 custom baseUrl에서 세션 헤더를 보내지 않습니다. cc-lb는 Senpi의 system prompt로 request_kind를 분류하고, cache prefix로 세션 없는 요청의 affinity를 유지합니다.

    Senpi의 --session-id를 observed_session_id로 기록하려면 전용 설정 디렉터리에서 sendSessionAffinityHeaders를 켭니다. API 키는 파일에 쓰지 않고 환경변수로 전달하면 child subagent도 상속합니다.

    bash
    export SENPI_CODING_AGENT_DIR="$HOME/.config/senpi-cc-lb/agent"
export SENPI_CODING_AGENT_SESSION_DIR="$HOME/.local/share/senpi-cc-lb/sessions"
mkdir -p "$SENPI_CODING_AGENT_DIR" "$SENPI_CODING_AGENT_SESSION_DIR"

cat > "$SENPI_CODING_AGENT_DIR/models.json" <<'JSON'
{
  "providers": {
    "anthropic": {
      "baseUrl": "http://127.0.0.1:8080",
      "compat": { "sendSessionAffinityHeaders": true }
    }
  }
}
JSON

ANTHROPIC_API_KEY=$CC_LB_PROXY_KEY \
  senpi --provider anthropic --model claude-sonnet-4-5 \
  --session-id my-senpi-session

    이 시점부터 모든 호출이 cc-lb를 통과하며 메트릭/감사 로그에 잡힙니다.

  10. 종료

    bash
    # 처리 중인 proxy 요청 wait + 종료
kill -TERM $(pgrep -f '[c]c-lb serve')

    SIGTERM은 drain_secs만큼 아직 응답을 만들고 있는 proxy 요청을 기다린 뒤 종료합니다. 이미 시작된 SSE 응답 body는 drain 대기 대상이 아니며, 클라이언트가 재연결해야 합니다. SIGINT(Ctrl-C)는 즉시 종료입니다.

어느 길로 가야 할까

아래 카드에서 본인 상황과 가장 가까운 항목을 누르세요. 각 use case는 같은 5단계 패턴입니다: 언제 / 현실 / 최소 config / 실행 / 확인.

가장 흔함

① 단순 프록시 + 로깅

키 하나, 클라이언트는 그대로, 중앙에서 로그·메트릭·감사만 보고 싶을 때. Quick Start와 거의 동일.

 rate limit 회피

② 여러 Anthropic 키 분산

한 키가 한계라서 여러 키로 트래픽 나누고 싶을 때. 현실: 빌트인 router는 첫 upstream만 씀. 실제 분산 방법 4가지.

 멀티 클라우드

③ Anthropic + Bedrock + Vertex 혼합

모델별로 다른 provider 쓰고 싶을 때. SigV4 / GCP ADC 자동 처리.

 키 보호

④ 내부 키 → 실제 키 매핑

팀에 발급한 내부 키 ck-internal-*를 실제 Anthropic 키로 매핑. 실제 키 절대 노출 X.

 구독자

⑤ Claude Pro OAuth 토큰

Claude Pro 구독 토큰 (sk-ant-oat01-*)을 cc-lb 뒤에서 운영 — 연결하면 항상 365일 long-lived 토큰을 요청하고, 안 되면 자동 refresh로 fallback.

Use Case ① · 단순 프록시 + 로깅

언제

  • Anthropic 키 한 개를 팀 전체가 공유하고 있는데, 누가 얼마나 쓰는지 보고 싶다.
  • 요청/응답을 감사 로그로 남기고 Prometheus로 SLO 보고 싶다.
  • 클라이언트 코드/설정은 최소 변경.

현실

  • Plugin 없이 DB principal과 DB upstream만으로 동작합니다. 즉시 동작
  • 클라이언트는 principal에 발급된 managed API key를 보냅니다. Principal kind는 해당 DB principal에서, upstream kind는 라우터가 선택한 DB upstream에서 가져옵니다.

최소 config 발췌

toml
[storage]
kind = "sqlite"
path = "./data/cc-lb.sqlite"

[observability]
tracing_level = "info"
log_redaction = true

실행 + 확인

Quick Start 그대로 따라가면 됩니다. cc_lb_requests_total이 호출마다 올라가는지만 확인하세요.

Use Case ② · 여러 Anthropic 키 분산

언제

  • 키 하나의 organization-level rate limit이 한계라서 여러 키로 트래픽을 분산하고 싶다.
  • 키 별로 다른 결제/조직으로 쓰고 싶다.

현실 (꼭 읽기)

안내 cc-lb는 filter chain과 terminal strategy로 upstream을 선택합니다. filter plugin은 후보를 검증하거나 줄이고, terminal strategy는 남은 후보 중 최종 upstream을 고릅니다. 별도 filter가 없으면 principal의 allowed upstream 목록과 terminal strategy만으로 동작합니다.

추천 해결책: random terminal strategy 사용

여러 키에 트래픽을 나누는 가장 단순한 방법은 여러 upstream을 등록한 뒤 principal의 terminal strategy를 random으로 설정하는 것입니다. 고급 정책이 필요하면 filter plugin으로 후보를 먼저 줄이고 같은 terminal 단계로 최종 선택을 맡기세요.

terminal strategy 설정 예시

bash
# POST /admin/v1/upstreams 로 여러 upstream 등록 (예: anthropic_pool_a, anthropic_pool_b)
# PUT /admin/v1/principals/{principal_id}/router-terminal 로 최종 선택 전략 설정
curl -X PUT http://127.0.0.1:9090/admin/v1/principals/api-key/router-terminal \
  -H "Authorization: Bearer $CC_LB_ADMIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"strategy":"random"}'

필터 플러그인이 필요한 경우

캐시 상태, quota, 조직별 정책처럼 단순 무작위 선택 전에 후보를 줄여야 하는 조건은 filter plugin에서 처리합니다. filter는 사용 가능한 upstream 후보 목록을 받아 유지할 후보 ID만 반환하고, terminal strategy는 그 결과 위에서 최종 upstream을 선택합니다.

확인

bash
# 1. principal의 terminal strategy 확인
curl -s http://127.0.0.1:9090/admin/v1/principals/api-key/router-terminal \
  -H "Authorization: Bearer $CC_LB_ADMIN_TOKEN"

# 2. 서로 다른 요청을 여러 번 호출하여 upstream 선택이 바뀌는지 확인
curl -s http://127.0.0.1:8080/v1/messages -H "x-api-key: keyA" ...
curl -s http://127.0.0.1:8080/v1/messages -H "x-api-key: keyB" ...

# 3. 메트릭에서 각 upstream 별 요청 수 확인
curl -s http://127.0.0.1:9091/metrics | grep cc_lb_requests_total

Use Case ③ · Anthropic + Bedrock + Vertex 혼합

언제

  • 일부 모델은 AWS Bedrock에 enroll, 일부는 GCP Vertex, 일부는 Anthropic Direct.
  • 클라이언트는 Anthropic API 하나만 알면 되고, cc-lb가 뒷단을 알아서 처리.

현실

  • 4가지 signer가 자동 처리됩니다: api_key, anthropic_oauth, aws_sigv4, gcp_oauth. 검증됨
  • Bedrock 응답의 AWS event-stream은 cc-lb가 Anthropic SSE 형식으로 자동 변환합니다.
  • Bedrock/Vertex의 에러 JSON도 Anthropic 에러 형식으로 자동 normalize됩니다 (성공 응답은 그대로 passthrough).
  • 모델별 허용/거절은 principals..allowed_models로 처리하고, upstream 후보 조정은 filter plugin 또는 terminal strategy로 처리합니다.

최소 config 발췌

toml
# Create provider upstreams with POST /admin/v1/upstreams.
# Bedrock/Vertex credentials still come from the standard AWS/GCP environments.
# Upload model_router.wasm with POST /admin/v1/plugins/wasm, then attach it with
# POST /admin/v1/principals/{principal_id}/plugin-chain.

실행 + 확인

bash
# AWS / GCP credential은 표준 위치에 있어야 함
export AWS_PROFILE=default
export GOOGLE_APPLICATION_CREDENTIALS=~/.config/gcloud/application_default_credentials.json

./target/debug/cc-lb config validate --config mix.toml
./target/debug/cc-lb serve --config mix.toml

# 본인이 enroll된 Bedrock 모델 ID로 호출
curl -s http://127.0.0.1:8080/v1/messages \
  -H "x-api-key: $CC_LB_PROXY_KEY" \
  -H "anthropic-version: 2023-06-01" \
  -d '{
    "model": "anthropic.claude-sonnet-4-5-20250929-v1:0",
    "max_tokens": 16,
    "messages": [{"role":"user","content":"hi from bedrock"}]
  }'
주의 Bedrock/Vertex 모델 ID는 provider 형식을 그대로 본문 model에 넣어야 합니다 — cc-lb는 변환하지 않습니다 (이건 의도, 모델명 자동 변환은 scope 밖).

Use Case ④ · 내부 키 → 실제 키 매핑

언제

  • 팀원/CI에 실제 sk-ant-api03-* 키를 절대 노출하고 싶지 않다.
  • 내부 키 ck-internal-alice를 발급해서 cc-lb가 실제 키로 바꿔준다.
  • 내부 키 회수/회전이 클라이언트 재배포 없이 가능.

현실

  • examples/plugin-internal-key-mapping/가 정확히 이 use case 예제입니다. 동작 검증됨 (T35)
  • plugin이 들고 있는 매핑은 in-memory. 영속화하려면 plugin storage API (cc_lb_storage_get/put) 사용.

최소 config 발췌

toml
[storage]
kind = "sqlite"
path = "/var/lib/cc-lb/cc-lb.sqlite"

[aead]
key_env = "CC_LB_MASTER_KEY"

# Create the upstream with POST /admin/v1/upstreams.
# Upload plugin_internal_key_mapping.wasm with POST /admin/v1/plugins/wasm,
# then attach it with POST /admin/v1/principals/{principal_id}/plugin-chain.

빌드 + 실행

bash
rustup target add wasm32-wasip1

Use Case ⑤ · Claude Pro OAuth 토큰

언제

  • 본인이 Anthropic Pro 구독자이고 sk-ant-oat01-* 토큰을 cc-lb 뒤에 두고 싶다.
  • 토큰 자동 관리(365일 long-lived, 불가 시 자동 refresh) + 안전한 저장이 필요하다.

현실

  • examples/plugin-oauth-anthropic-pro/ + anthropic_oauth signer 조합. 자동 refresh + single-flight 검증됨 (T15)
  • 토큰은 sqlite에 ChaCha20-Poly1305로 AEAD 암호화되어 저장됩니다. 마스터키 (CC_LB_MASTER_KEY) 없으면 복호화 불가.
  • 최초 토큰 등록은 admin REST의 PKCE 흐름으로 합니다 (POST /admin/v1/upstreams/{upstream_id}/oauth/start → 본인 브라우저에서 인증 → callback → POST /admin/v1/upstreams/{upstream_id}/oauth/complete).
  • 연결은 항상 365일 long-lived 토큰을 요청하며 모드 선택은 없습니다. 결과 credential은 long_lived_365d (365일 access token, token refresh는 절대 안 함 — 1년에 한 번 정도 재인증) 또는 refreshing (기존 8시간 토큰 + 자동 refresh — 약 30일마다 재인증) 둘 중 하나로 저장되고, 어느 쪽인지는 cc-lb가 스스로 결정합니다. token refresh를 제외한 quota polling, warm-up bootstrap/watchdog, subscription-metadata 자동 refresh, 인증 실패 보고는 두 모드에 똑같이 적용됩니다.
  • 기본 요청 scope는 user:profile + user:inference입니다 — 이 inference-only 조합이 1년짜리 토큰을 가능하게 합니다. org:create_api_key를 명시적으로 설정한 운영자는 그 설정을 유지하지만 Anthropic이 year-long token을 부여하지 않으므로 연결은 refreshing 모드로 fallback하고 cc-lb가 그 이유를 보고합니다. Remote Control (user:sessions:claude_code), 커넥터 (user:mcp_servers) 같은 다른 scope도 부여 수명을 짧게 만들 수 있습니다.
  • long-lived credential의 refresh token은 저장되지만 절대 사용하지 않습니다 — 사용하면 Anthropic이 365일 토큰을 회수하고 8시간짜리로 교체합니다. 인증이 거부되면 주기적인 usage poll이 그 실패를 기록하고 upstream에 reconnect prompt를 표시하며, rotation으로 복구하지 않고 재인증이 필요합니다.
  • cc-lb는 token endpoint가 실제로 반환한 access token 수명을 그대로 저장합니다 — 요청한 365일을 가정하거나 대체하지 않습니다. Anthropic이 365일 요청을 거절하면(400 invalid_request) 같은 authorization code로 custom expiry 없이 자동 재시도하고, 교환은 받아들이되 요청보다 훨씬 짧은 수명을 부여하면(clamp) 그것도 long-lived 거절로 간주합니다. 두 경우 모두 credential은 refreshing 모드로 유지되어 저장된 refresh token이 갱신 경로로 남고, upstream이 갱신 수단 없이 조용히 만료되는 일이 없습니다.
  • clamp 기준은 30일입니다 — Anthropic refresh token이 30일 윈도우에 고정되어 있어, 그 윈도우를 넘지 못하는 grant는 refreshing과 다를 바 없으면서 갱신 능력만 잃기 때문입니다. 30일을 넘지만 365일보다 짧은 grant는 long-lived를 유지하며 부여된 값 그대로 저장됩니다. complete 응답의 fallback_reason이 rejected, clamped, scope_rejected를 구분해 보고하고 granted_expires_in_secs에 실제 부여된 수명이 담기며, clamp는 warning 로그도 남겨 조용한 Anthropic 정책 변경이 운영에서도 보이게 합니다.

최초 토큰 등록 (PKCE)

Admin UI의 upstream 생성 wizard와 Reconnect 모달은 모드 선택 없이 항상 365일 long-lived 토큰을 요청합니다. token endpoint가 거절하거나 부여 수명이 30일 refresh-token 윈도우를 넘지 못하면 cc-lb가 알아서 refreshing credential로 저장하고 그 사실을 보고합니다 — long-lived는 1년에 한 번 정도, refreshing은 약 30일마다 재인증합니다.

bash
# 1) 인증 URL 받기 (항상 365일 long-lived 요청, body는 빈 객체)
curl -s -X POST http://127.0.0.1:9090/admin/v1/upstreams/$UPSTREAM_ID/oauth/start \
  -H "Authorization: Bearer $CC_LB_ADMIN_TOKEN" \
  -H "content-type: application/json" \
  -d '{}'

# 2) 브라우저가 콜백한 code를 cc-lb에 전달 (PKCE verifier는 1단계에서 받은 값)
curl -s -X POST http://127.0.0.1:9090/admin/v1/upstreams/$UPSTREAM_ID/oauth/complete \
  -H "Authorization: Bearer $CC_LB_ADMIN_TOKEN" \
  -H "content-type: application/json" \
  -d '{"state_token":"...","code":"..."}'

Config editor와 저장

    
관리 UI는 /admin/v1/config/editor에서 파일의 writable/read-only 상태와 revision을 읽습니다. 초안은 /admin/v1/config/draft로 조회·저장하고, 저장 전에 /admin/v1/config/draft/validate를 호출하세요. 검증 결과는 초안의 last_validation JSON으로 확인할 수 있습니다.

    
/admin/v1/config/save는 expected revision과 파일 fingerprint를 확인한 뒤 초안을 파일에 저장합니다. 저장 이력은 /admin/v1/config/history에서 metadata-only로 조회하고, /admin/v1/config/draft/download로 초안을 내려받습니다. 저장한 설정은 실행 중인 프로세스에 즉시 반영되지 않으며 항상 프로세스 재시작 후 적용됩니다.


    
Graceful drain

    
bash
kill -TERM $(pgrep -x cc-lb)
# 1. proxy listener는 새 요청 503 + Retry-After: 60 반환
# 2. 응답 생성 중인 proxy 요청은 timeouts.drain_secs 까지 대기
# 3. 이미 열린 SSE body stream은 기다리지 않음 (클라이언트 재연결 필요)
# 4. admin/metrics 리스너는 drain 중에도 살아있음 (메트릭 계속 scrape 가능)

알려진 한계

    
    
      
  • terminal strategy는 단순 선택만 담당 — 가중치, 연결 수, 외부 상태 기반 정책은 filter plugin으로 후보를 줄인 뒤 적용해야 합니다. Use Case ② 참고.
    • 
      
  • 모델명 자동 변환 없음 — Bedrock/Vertex 모델 ID는 본문 model에 provider 형식 그대로 보내야 합니다.
    • 
      
  • cross-LLM 변환 없음 — Anthropic Messages API 형식만 지원. OpenAI/Gemini 형식 변환은 scope 밖.
    • 
      
  • 스트리밍 ↔ 비스트리밍 변환 없음 — 요청 그대로 forwarding.
    • 
      
  • 응답 캐싱 없음 — 매 요청마다 upstream 호출.
    • 
      
  • 분산 모드 없음 — 단일 인스턴스 전제. 여러 인스턴스 띄우려면 Postgres가 필요합니다.
    • 
      
  • HTTP/3 / gRPC / WebSocket 없음 — Anthropic API가 HTTP/1.1+HTTP/2 SSE 기반이라 그 외 프로토콜은 미지원.
